## Stack

## Non-obvious conventions (verified against this project's own `node_modules/next/dist/docs`, not memory — Next 16 shipped breaking changes after most training data)

- **`src/proxy.ts`, not `middleware.ts`.** Next 16 renamed the file/export (`middleware` filename is deprecated). Export a function named `proxy`. It always runs on the Node.js runtime here (no edge option).
- **Admin routes live at a real `app/[locale]/admin/` segment**, never a `(admin)` route group — groups are stripped from the URL and would make admin pages indistinguishable from public ones to `proxy.ts`'s matcher.
- **`params`/`searchParams` are Promises** in `page.tsx`, `layout.tsx`, and Route Handlers (`await params`) — fully async-only as of v16, no sync fallback.
- **Defense in depth on the admin gate**: `proxy.ts` is the first check, but re-verify session + role inside `app/[locale]/admin/layout.tsx` (Server Component) and inside every admin-only Route Handler individually. Don't rely on proxy/middleware alone (see Next's own CVE-2025-29927 note in the proxy docs).
- **RLS is the real security boundary**, not app code. Every DB access goes through `@supabase/supabase-js` (anon key client-side/RLS-scoped, service-role key only in server-only code) so policies are always enforced. `profiles.role` is never client-settable.
- **Storage/chain are adapters, mock by default.** `src/lib/storage/ipfs/index.ts` and `src/lib/chain/index.ts` pick mock vs. real via env vars (`STORAGE_PROVIDER`, `CHAIN_PROVIDER`). Real adapters (Pinata JWT, chain deployer key) are only ever instantiated inside server Route Handlers — never `NEXT_PUBLIC_*`, never imported into a Client Component. Mock output is always visibly badged in the UI ("Mock IPFS", "Mock chain") — never silently indistinguishable from real.
- **No namespace ships with missing Bangla keys.** Every `messages/en/*.json` file has a matching `messages/bn/*.json` with the same key set — author both together, same commit. `scripts/check-i18n-parity.ts` enforces this.
- **Theme tokens** (defined in `src/app/[locale]/globals.css` under `@theme`): green `#006A4E` is `--primary`, red `#F42A41` is `--destructive` only (never remap shadcn's neutral `--accent` token to red — it drives incidental hover states across every primitive). Amber is a functional status color only (medium-risk/pending), not a brand accent.
- **Seed/demo data must use fictional placeholder personas only** — never real July 2024 victims' names/photos without a separate, explicit sourcing/consent process.
- Verify exact package APIs against installed `node_modules` docs/types before use, don't trust training-data defaults — this project intentionally tracks current majors (Next 16, Tailwind v4, React 19) that shipped after most model training cutoffs.
- **`supabase config push` pushes the entire `[auth]` config section, not a single field.** It has no `--dry-run`. Before running it against the linked (already-configured) remote project, diff it first (it prints a diff and prompts); a locally-scaffolded `config.toml` has local-dev-oriented defaults (email confirmation off, weak OTP rate limits, MFA off, `127.0.0.1` site URL) that will silently overwrite real project settings otherwise.
- **shadcn/ui here is built on Base UI (`@base-ui/react`), not Radix.** Polymorphic composition uses a `render={<Element />}` prop, not `asChild`. When swapping a `Button`/`SheetClose`/etc. to render a non-button element (e.g. a `Link`), pass `nativeButton={false}` or Base UI logs a console warning about lost button semantics.
- Known benign dev-only console warning: `next-themes` injects an inline `<script>` to prevent theme-flash before hydration, which trips React/Next 16's "script tag encountered while rendering" dev warning. This is `next-themes`' own implementation (see `src/components/theme-provider.tsx`), not an app bug — doesn't appear in production builds, theme switching works correctly.
- Known benign dev-only console warning: nesting a `Button` inside `SheetTrigger`/`SheetClose`'s `render` prop (two layers of Base UI polymorphic composition) logs a hydration mismatch on the `data-slot` attribute only (`"button"` vs `"sheet-trigger"`/`"sheet-close"`). This is shadcn's own default generated `sheet.tsx` pattern, not something specific to this app's code — no functional/accessibility impact observed (verified the Sheet opens/closes correctly in a real browser), `data-slot` is CSS-targeting-only.
- Supabase Auth redirect URLs (`emailRedirectTo` in `signInWithOtp`, etc.) must match `auth.site_url` or an entry in `auth.additional_redirect_urls` (wildcards like `http://localhost:3000/**` work) in `supabase/config.toml`, or the request 400s. Also note real rate limits apply even in dev (`auth.email.max_frequency`, plus a stricter IP-based limit) — don't hammer `signInWithOtp` in quick succession while testing.
- **Nested translation namespaces**: `getTranslations({namespace: "common"})` scopes `t()` to that object — a key like `nav.adminPanel` still needs `t("nav.adminPanel")`, not `t("adminPanel")`. Missing keys don't crash the page (next-intl renders an inline `MISSING_MESSAGE` error in dev) so this class of bug is easy to miss without an actual browser check of every screen a change touches.
- **Admin magic links use a server-verifiable token hash.** The hosted Supabase Magic Link template must link to `{{ .RedirectTo }}&token_hash={{ .TokenHash }}&type=email`; the local equivalent is `supabase/templates/protocol-magic-link.html`. The callback also accepts PKCE `?code=` links for backwards compatibility, validates that `next` stays inside the localized admin route, and rejects non-admin claims after session creation.
- **Forensic pipeline is real, not stubbed**: ELA (Canvas diff/amplify), dHash (9x8 grayscale), and Tesseract.js OCR (`eng+ben`) all genuinely work client-side — verified end-to-end against a synthetic test document (92% OCR confidence, exact NID/date extraction). Two benign Tesseract.js console warnings ("Parameter not found: segsearch_max_futile_classifications" / "classify_misfit_junk_penalty") are normal engine noise, not errors.
- **Calling a Server Action directly from a Client Component (not via a `<form action={...}>`) and then `router.push()`-ing to a new route afterward silently fails to navigate.** The RSC payload for the target route fetches successfully (visible in the Next dev log, 200/303) but the browser's URL/DOM never transitions — no thrown error, no console warning, just a page that looks stuck. Symptom is easy to misdiagnose as a hang. Fix: perform the redirect **inside the Server Action itself** via `redirect({href, locale})` from `@/i18n/navigation` (passed the current `locale` as an explicit action argument, since Server Actions have no implicit route-param context) instead of returning data and calling `router.push()` client-side. `router.refresh()` on the *same* route (no cross-route navigation) is unaffected — only the create-then-navigate-elsewhere pattern hits this. Because `redirect()` throws a `NEXT_REDIRECT`-digest error to signal navigation, client code awaiting the action must not swallow it: re-throw anything with `digest.startsWith("NEXT_REDIRECT")` before falling through to your error-alert branch.
- **Base UI's `<Select.Value>`/`<SelectValue>` does not auto-resolve the selected item's rendered label** the way Radix's does — with no children it just prints the raw `value` string (e.g. `criminal_prosecution` instead of "ফৌজদারি মামলা"). Always pass an explicit label-mapping function as children: `<SelectValue>{(value) => LABELS[value]}</SelectValue>` (or a `t(...)`/lookup-array call). Easy to miss because there's no error or warning — the dropdown *works*, it just displays the wrong text once a value is selected.
- **`src/app/api/dev/` holds two unrelated things**: the temporary `test-auth` route (add/delete per verification session, see below) and the permanent `local-ipfs/[cid]` route (real mock-storage file server, part of Phase 5, never delete). `rm -rf src/app/api/dev` deletes both — happened twice in this session. Delete `src/app/api/dev/test-auth` specifically, never the parent `dev/` directory.
- **`npm run i18n:check-keys` statically catches wrong-nesting-level translation key bugs** (calling `t("verification.pending")` when the translator is scoped to `admin.victims.form` but the key actually lives at `admin.victims.verification.pending`, a sibling of `form`) — next-intl only surfaces these as an inline `MISSING_MESSAGE` error in a real browser render, never a build/type error, so this bit twice during Phase 6 before the script existed. Run it alongside `i18n:check` (parity) before considering any admin form done; it can't check dynamic `t(\`ns.${value}\`)` calls, only string-literal ones, so a quick browser click-through of any new dropdown is still worth doing.
